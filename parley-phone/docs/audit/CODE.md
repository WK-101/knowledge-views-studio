# Parley: code quality, architecture, maintainability and feature coherence audit

Scope: all modules of `parley-phone` (app, core/common, core/data, core/ui, telecom, lists-updater), at HEAD `75f6acf` (Release 3.4.0).
Method: read-only. I read the key files and took measurements with grep and small Python scripts (duplicate-block detector, inline-FQN counter, translation-gap counter, notification-id scan). Every figure below comes from those runs. Where I infer something, I mark it "likely".

Measured sizes (main / test lines of Kotlin): core/common 18,090 / 10,055 (791 `@Test`s); core/data 12,632 / 0; core/ui 887 / 0; telecom 5,104 / 0; app 37,380 (195 files) / 0; lists-updater 793 / 0.

---

## 1. Summary and scores

Parley has a well-designed **module graph** around a very large and mostly untested **app layer**. The Gradle modules enforce the important boundaries:
- `core/common` is a pure JVM module, and the build rejects any Android import there.
- `telecom` cannot see `core/data`; it gets its data through the `TelecomDependencies` interface.
- The privacy and reproducibility tooling is unusually mature.

Most of the domain logic that can be pure has been pulled into `core/common` and is well tested (791 tests).

The problems are above the module line:
- There is **one `AppViewModel` for the whole app**. It publishes the whole `DataContainer` as `vm.c`, and composables use it directly **442 times in 89 files**.
- Business workflows (save contact, save meta, backgrounds, relations, vault moves) run in **203 `scope.launch` calls inside composables**, against 14 `viewModelScope.launch`.
- Screen state lives in hundreds of `remember { mutableStateOf }`. The contact editor loses its draft on rotation.
- Features were delivered in labelled waves (v3.1 to v3.4, item ids R/F/U/P/X/C/V…). That has left:
  - release-named files and strings (`PhoneV32.kt`, `strings_v34_*.xml`, `v34_*` keys);
  - about 1,350 item-id tags in code;
  - 342 strings (about 9% of the app's strings) untranslated in all 7 locales;
  - parallel implementations of the same concept: 6 phone-key schemes, 5 messenger registries, about 24 separate preference files, two sources of call data.

Error handling mostly swallows failures: 515 `runCatching`, 42 empty catches, only 26 log calls. At least one cross-feature bug came out of the uncoordinated waves: a **notification-id collision** between the backup-failure notification and missed-call notifications.

What is genuinely good:
- **`core/common` purity and its test suite.** Pure logic such as `PhoneNumbers`, `CallPolicy`, `BackupCrypto` and `VCardMapper` is tested with real regression cases (Arabic-digit locale tests, vCard round trips, crypto).
- **The telecom isolation contract.** `telecom/build.gradle.kts` documents "must never depend on :core:data", and `TelecomGraph` uses a `@Volatile` holder.
- **Build-time guards.** The forbidden-permission check (`app/build.gradle.kts:130-160`), `checkHardcodedText` and `checkLocaleFormat` (`build.gradle.kts:11-85`), and the updater's permission allow-list.
- **Room.** Exported schemas plus AutoMigrations 1→6, and no destructive fallback (`AppDatabase.kt:518-536`).
- **Main safety.** Repositories are main-safe (for example `ContactsRepository.load` uses `withContext(Dispatchers.IO)`, `ContactsRepository.kt:340`), and there is no `GlobalScope`.
- **`DataContainer.followKeyChanges`** correctly rethrows `CancellationException` (`AppContainer.kt:106-112`); this is the pattern to copy everywhere.
- **Documentation.** KDoc explains the why, which is rare and valuable.

## 3. Patterns and root causes

1. **Wave-driven delivery without a consolidation step.**
   Each release (v3.1 to v3.4) added a batch of item-ids (R1, F13, V34, …). New work went into new files named after the wave (`*V32.kt`, `strings_v34_*.xml`), new stores (`parley_call_extras`, `ux`, `messaging`, `bulk_add`) and new registries, instead of extending the existing ones. The item ids in code are the trace of this.
   **Systemic fix:** a "consolidation" definition of done for each wave: rename by domain, fold into the existing abstraction, add a backup decision, finish translations, register notification ids. Track the ids in the tracker, not in code.
2. **No presentation layer.**
   With one `AppViewModel` that publishes the container, adding a feature by writing a composable against `vm.c.*` is the path of least resistance. So workflows, entity construction and read-modify-write moved into composables (CQ-02/03/04/07). This is also why there are 0 app tests and 0 previews.
   **Systemic fix:** per-feature state holders or VMs with immutable `UiState`, following a small template, and a rule (detekt `ForbiddenImport` on `app.parley.data.db.*` in `ui/**`, or review policy) that UI never touches entities or DAOs.
3. **Container as service locator.**
   `DataContainer` is convenient but hides the graph. Late-bound callbacks and lambda cycle-breakers show that features are coupled (vault ↔ circle ↔ history ↔ contacts keys).
   **Systemic fix:** constructor-injected collaborators, a domain event stream for "contacts changed, calls forgotten, key moved", and a DI tool or interface-based graph so core/data can be tested with fakes.
4. **"Never crash" as the error policy.**
   For a dialer, avoiding crashes is right. Implemented as blanket `runCatching` and empty catches, it turns bugs into silent misbehaviour: backup sections disappear, cancellations become "save failed", notification collisions go unnoticed.
   **Systemic fix:** catch at boundaries only, rethrow cancellation, log non-fatals (to the existing opt-in CrashStore), and surface failures in results (the backup report).
5. **The test boundary equals the module boundary.**
   Only the pure JVM module is tested, because the rest would need Android. The extraction strategy is right and should continue (e.g. a CallManager reducer), but it needs to be complemented by Robolectric or instrumented tests for the data layer and migrations, plus CI.
