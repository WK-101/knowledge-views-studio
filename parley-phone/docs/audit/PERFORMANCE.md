# Parley: performance, responsiveness, battery, startup, APK size (audit)

Scope: `parley-phone/` only. Read-only review. Measurements come from the release APK and R8 mapping already in `app/build/outputs` (built Sep 27 03:36): `app-release.apk` is 14.45 MB and holds 8171 retained classes. Paths below are relative to `parley-phone/`.

## 1. Summary and scores

Parley's hot paths are well designed in several places:
- Keypad search narrows incrementally (`DialSearch`).
- Recents loads in two stages: a 100-row preview, then the full log.
- Spam lists are memory-mapped.
- Screening has hard timeouts and fails open.
- Avatars are decoded with sampling and kept in an LRU cache.
- Widget work runs through `goAsync`.
- `StateFlow` equality stops identical contact lists from propagating.
- R8 and resource shrinking are on, and the ez-vcard extras are excluded.

The weaknesses are systemic rather than local:
1. **Every process start builds everything.** A cold start for an incoming call, a Worker, a widget or a broadcast eagerly runs:
   - the full contacts load (3 provider scans)
   - the call-log load (up to 3000 rows, twice)
   - decryption of the whole call archive
   - the `CallLogIndex` build
   - the `PeopleIndex` scans (3 more queries)
   - a lookup-key sweep with N+1 queries 15 s later

   All of this competes with the 1.5 s screening budget.
2. **The app-wide flows are hot forever.** There are 32 `SharingStarted.Eagerly` flows against 4 `WhileSubscribed`. A permanent collector in `CircleWidget.observe` pins the history index even when no widget exists.
3. **Some list work still runs on the main thread**:
   - Recents computes a date header for every group inside the `LazyColumn` content lambda.
   - The keypad's contact search filters the whole address book in composition.
   - `NumberInfo.location` (libphonenumber plus the geocoder) runs in composition and in the telecom `publish()`.
4. **There is no debounce on the contacts observer.** Each sync batch reloads the address book.

## 3. Patterns and root causes

1. **The container doubles as a warm cache for everything.** `DataContainer` is shared by the UI, the call path, workers, receivers, tiles and widgets, and its core repositories start eagerly. Any component that touches `c.X` pulls in the whole dependency graph (`people` → `PeopleIndex` → scans, `history` → decrypt). *Systemic fix:* split into a small **CallPathGraph** (settings, rules, lists, vault lookup, contacts lookup) and a lazily started **UiDataGraph**. Tie the observed flows to subscribers (`WhileSubscribed`) instead of `Eagerly`. Guard with a debug-only `Trace` or `StrictMode` check in `Application.onCreate`.
2. **A full reload is the only refresh strategy.** Every content-observer tick re-reads whole tables (contacts ×3, `PeopleIndex` ×3, call log 3000 rows, archive ids) and rebuilds derived indexes. There is no debounce and no delta. *Fix:* debounce, cheap change detection (for example `Contacts` count plus max `CONTACT_LAST_UPDATED_TIMESTAMP`, or `Calls` max `_ID`/`DATE`) before a full scan, and incremental archive sync (already partly done).
3. **Derived UI data is computed in composition.** Headers, sections, text search, geocoding and date formatting run in `@Composable` or `LazyListScope` bodies. The ViewModel already has Default-dispatched pipelines. Extend them to produce display-ready row models (header rows, formatted time, location, section letter) so lists become `items(rows, key, contentType)` with trivial item bodies.
4. **Synchronous-constructor stores.** Around 18 SharedPreferences-backed stores parse on first touch, wherever that touch happens. Standardise on an async-loading store (like `SettingsRepository`'s `loaded` flag), or warm them on IO before the first UI or call use.
5. **No performance guardrails.** There is no StrictMode in debug, no Macrobenchmark or baseline profile, no `Trace` sections on the call path, and no APK-size budget. Regressions like P1 and P4 are only seen on slow phones with large logs.

**Quick wins (≤1 day each)**

### What is already good
- `DialSearch` candidate narrowing (`DialSearch.kt:53-69`).
- V11 two-stage call-log load (`CallLogRepository.kt:36-41`).
- Index built with a 200 ms debounce on Default (`CallHistory.kt:129-133`).
- mmap'd spam packs (`SpamListStore.kt:128-142`).
- Screening fails open with hard timeouts, and `ScreeningGuard` avoids re-screening.
- Avatar decode uses bounds, sampling and an LRU.
- Widgets use `goAsync` and a thread, and `updatePeriodMillis=0`.
- The ringtone boost runs on an executor.
- Wake locks have timeouts and are not reference-counted.
- No `BOOT_COMPLETED` receiver.
- The private directory provider is disabled by default and never blocks when the container isn't ready.
- R8 with resource shrinking; ez-vcard jsoup/freemarker/jackson excluded; debug logs stripped.
