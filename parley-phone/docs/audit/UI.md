# Parley audit: UI consistency, design system and UX coherence

Scope: `app/src/main/kotlin/app/parley/ui/**`, `app/.../messaging/**`, `telecom/.../ui/**`, `core/ui/**` (173 Kotlin files, 34.8k lines), plus `app/src/main/res/values*` and `docs/WRITING.md`. Read-only review at 75f6acf (Release 3.4.0). The counts come from grep/python over those files. Where a line says "likely", it is inferred and was not run.

## 1) Summary

Parley's UI is careful at the level of single widgets. It uses only one icon family (Rounded + AutoMirrored.Rounded, with 0 Filled/Outlined/Default). IconButtons almost always carry a content description (1 borderline case in the whole scope). Swipe rows have TalkBack custom actions, the fast-scroll rail has adjustable semantics, keypad digits cap font scaling, and colours are mostly theme tokens. Hard-coded hex values live only in `core/ui`, apart from intentional white QR backgrounds and call green/red. Settings search with scroll-to-and-flash (`LocalHighlightKey`) is a strong feature.

The weak points are the **system** and the **product**:
- `core/ui` is thin (887 lines). The real building blocks (SwitchRow, LinkRow, SettingsScaffold, section headers, cards) live in `app/ui/settings` or are rebuilt per feature.
- Screens use at least 3 visual languages: segmented settings cards, flat ListItem lists with divider "Section"s, and the Blocking "BlockingCard / CollapsibleSection" style.
- About 9.3% of English strings (341 of 3,733) are **English-only v3.3/v3.4 strings**. They sit on the most-used surfaces (Recents rows, contact page section titles, keypad call pill, Message/Call on) in a 7-language app with 2 RTL languages. This contradicts WRITING.md ("Every new string follows this guide, in all 8 languages").
- Conceptual overlap has grown release by release. Examples: Favourites, Circle, Labels, Speed dial, Frequent and "Allow through DND" (which stars people). There are three "Recently deleted" style places, three names for Blocking and three names for Insights. The overflow menu reaches about 18 items. Settings has 109 catalogued entries on 12 pages plus about 20 settings-like sub-screens with their own layouts.

## 3) Patterns and root causes

1. **Feature-by-release development without a component layer.** Each version (v3.2 Circle, v3.3 surfaces/QR/glance, v3.4 contact page/messaging/keypad) added its own rows, headers, sheets and strings file. `core/ui` stopped at nine small files. The components that are shared in practice (SwitchRow, LinkRow, SettingsScaffold) sit in `app/ui/settings`, so new features in `messaging/` or `blocking/` rebuild them (ToggleRow, calltime.ChoiceRow, BlockingCard, SheetSection). **Systemic fix:** grow `core/ui` into a real kit (scaffolds, top bar, rows, section header, confirm/info dialog, sheet, banner, spacing/shape/motion tokens), and add a detekt/lint rule that flags `TopAppBar(`, `AlertDialog(`, `RoundedCornerShape(` and `Toast.makeText` outside core/ui.
2. **"English now, translate later" as a routine.** Seven files are marked `tools:ignore="MissingTranslation"`, and `lint.xml` downgrades MissingTranslation to a warning. That makes it structurally easy to ship 9% English on the most visible screens. The hard-coded-text checker is regex-based and misses `actionLabel`. **Fix:** release gate on key-set parity for shipped locales, drop the per-file ignores, and extend the checker patterns.
3. **Additive UX with no pruning.** Each feature added an entry point (menu item, settings row, section, FAB) and none was removed, so the same destination is reachable from 3–4 places under different names. Layout options (combined surfaces, Circle placement, favourites strip, density, simple mode) multiply the states that have to stay coherent. **Fix:** a concept glossary (one name per concept), an entry-point map per destination with a maximum of 2, and a periodic "remove or merge" pass. Treat layout toggles as costly.
4. **Accessibility is done per widget, not per pattern.** IconButtons and swipe rows are well labelled because each author handled them. Section headers, sticky headers and contrast are missed because no shared component enforces them.
5. **Theme tokens are declared but not used.** The shape scale and motion scheme exist in `ParleyTheme`, but call sites don't read them. Tokens are only followed when they are the easiest option (MaterialTheme.typography is; shapes and motion aren't).
