# Parley Phone: security and privacy audit

Scope: `parley-phone/` (app, telecom, core/*, lists-updater, build files). Threat models: a malicious installed app; a malicious QR code, vCard, file or link; a lost or unlocked phone; a shoulder surfer; someone who steals a backup file or has access to the sync folder; a spoofed companion app. Read-only review. Every claim cites the code it rests on; "likely" marks an inference.

## 1. Summary and scores

Parley's security engineering is well above average for an open-source dialer. The backup envelope is a correct STREAM/AES-GCM construction with the header as authenticated data. Every PendingIntent is immutable and explicit. No receiver is exported without protection. The private-name providers pin each approval to the approving app's signing certificate. No module can gain INTERNET or other dangerous permissions without failing the build. `allowBackup="false"` and exclude-all extraction rules are set in both apps.

The weak spots sit in three places:
- **Operational key handling.** The release signing key is plaintext, world-readable, and kept on ephemeral `/tmp`.
- **Places where a feature defeats the protection it sits next to.** Examples: a wildcard matcher that can hang the call screener; a notification action that grants access to private names from the lock screen; a companion check that always passes; a recovery key copied to the clipboard in plain view.
- **App-lock edge cases.** These include recents thumbnails, an asynchronous lock decision, fail-open on odd biometric statuses, and exported entry points that bypass the lock.

| Sub-area | Score /10 | One-line justification |
|---|---|---|
| 1. Manifests and exported components | 8 | Tight: every exported component is required by the platform or protected; no backups. Minus: no tapjacking defences, and Android 10 still gets StrandHogg-style affinity with singleTask. |
| 2. PendingIntents, IPC, URIs | 8 | All PendingIntents immutable and explicit; no intent redirection; FileProvider limited to cache subfolders. Minus: stream URIs taken from any sender (file://, own authorities), and JOIN_CONTACT acts on the caller's target. |
| 3. Cryptography | 7 | Backup crypto is excellent. Minus: the vault detail key can silently stay without authentication and has a data-loss path; archives can be forged by anyone with the embedded public key; PBKDF2 without a strength check. |
| 4. App lock | 5.5 | Covers MainActivity, the picker and widget configuration. Minus: recents thumbnails, an async lock at onStart, fail-open, NumberActionActivity and the QS tile, and a lock-screen approval action. |
| 5. Data leakage | 7 | Good lock-screen public versions and log stripping, with sensitive clip flags in several places. Minus: recovery key and numbers go to the clipboard without the sensitive flag, folder sync writes plaintext, and at-rest sealing is inconsistent. |
| 6. Input handling | 5.5 | Archives, packs, templates and simple-mode import are bounded, and USSD/MMI handling is safe. Minus: a wildcard ReDoS, and several unbounded `readBytes()`/gunzip calls. |
| 7. Companion (Parley Lists) | 6.5 | Good split (INTERNET only there, permission allow-list, HTTPS-only redirects). Minus: `canRead()` is always true and the provider package is never verified; pack trust is self-certified TOFU. |
| 8. Supply chain and build | 4 | Reproducible-build script and permission guards exist. Minus: signing key and passwords in plaintext in `dist/` and `/tmp`; no dependency verification metadata; guards cover only `assemble*`; no CI for this project. |
| **Overall** | **6.5** | Solid design, a handful of concrete holes, and weak release hygiene. |

### What is genuinely good (brief)
- `allowBackup="false"` plus exclude-all `data_extraction_rules` in both apps. The FileProvider is limited to three cache subfolders, and plaintext exports are cleaned at start and hourly (`ExportFiles.cleanup`).
- Every PendingIntent is `FLAG_IMMUTABLE` and explicit. There are no dynamic exported receivers. `MissedCallReceiver` requires `MODIFY_PHONE_STATE`, and `VoicemailRepository` targets its broadcast with `setPackage`.
- The private-name providers (`PrivateNameProvider`, `PrivateDirectoryProvider`) allow one exact number per query and 60 queries per hour, pin approvals to the certificate's SHA-256, trust `callerPackage` only from the Contacts Provider, keep the component disabled until opted in, and log without numbers.
- The backup envelope is well done: STREAM segments with counter and last flag, header as AAD, bounded parser, zip-bomb limits in `BackupArchiveReader`, and a recovery key with checksum.
- The lists updater uses a permission **allow-list** and rejects `sharedUserId`. Downloads are HTTPS-only (including redirects), carry no identifiers, and are size-capped after gunzip.
- The MMI/USSD dial guard (tel: links and QR codes only prefill the keypad). Simple-mode import normalises numbers and imports disabled. Templates are bounded and signed.
- Lock-screen notification public versions, `setAuthenticationRequired` on Block, and FLAG_SECURE defaulted on until settings load (`NumberActionActivity`, `InCallActivity`). Sensitive-clip flags in CopyAsText and MessageOnSheet.

## 3. Patterns and root causes

1. **Per-feature security instead of shared primitives.** Each surface re-implements its guard, and some copies drift:
   - Clipboard: three variants, one without the flag (SEC-05).
   - Notification actions: some require authentication, the private-name approval does not (SEC-04).
   - Bounded reads: the archive has `VerifyingInput`, while CSV, simple-setup and QR code do raw `readBytes()` (SEC-15).
   - URL safety: QR only (SEC-21).
   - Lock-screen gating: memory yes, note no (SEC-20).

   Systemic fix: a small `security` package with `SafeClipboard.copy(sensitive = true)`, `SecureAction.build(...)` (authentication required by default), `Bounded.read(stream, cap)`, `Links.open()` (always via UrlSafety) and `LockGate.canShow(kind)`. Add a lint rule or detekt check that bans the raw calls.
2. **The app lock is a UI overlay, not a gate.** `AppLock.locked` is a global flag that each activity chooses to observe, so every new exported entry point (NumberActionActivity, tiles, widgets, notification actions) needs its own decision, and several made a weaker one (SEC-06/07/13/14/22). Systemic fix: one `LockedEntryActivity` trampoline, or a base `LockedActivity` that authenticates before `setContent`, sets FLAG_SECURE and recents protection when locked, and locks at `onStop`. Add a manifest audit test that each exported component is either in the lock-exempt allow-list (in-call, picker-with-lock…) or extends the base.
3. **Trust bootstrapped from data the attacker also has.** Self-certified pack keys, backup public keys embedded in every archive, a companion "verified" by a permission Parley grants itself (SEC-03/09/24). Systemic fix: anchor trust in something outside the attacker-controlled blob. That means Parley's own signing certificate for the companion, a device Keystore key for backups, and a first-seen pinned key per pack ID shown to the user.
4. **Fail-open defaults for availability.** These are the right instinct for a dialer (calls must ring), but they bleed into security decisions: `canAuthenticate != SUCCESS` unlocks (SEC-07), an unauthenticated key is created and never upgraded (SEC-08), and any `InvalidKeyException` becomes "lost, re-seal" (SEC-08d). Fail-open should apply only to call delivery, never to authentication or to destructive key recovery.
5. **Release engineering lags code quality.** Strong in-code guards, but plaintext keys in the tree, no dependency verification and no CI (SEC-01/12).

## 4. Prioritized improvement plan

**Immediately (before the next release, under 1 day in total)**
1. SEC-01: move and rotate the signing key; delete `dist/parley-signing.txt`; `chmod 600`; separate passwords; keep an offline backup. If `dist/` was ever shared, treat the key as compromised and plan a v3 rotation.
2. SEC-02: replace the wildcard regex with a linear glob matcher, and add a 200-star test.
3. SEC-03: verify the companion provider's package signature before reading, and fix `canRead()`.
4. SEC-04: `setAuthenticationRequired(true)` on private-name Allow and Deny, or route them through a locked screen.
5. SEC-05: the sensitive clip flag in `Intents.copy`, and remove or flag the recovery-key copy.

**Quick wins (1–3 days)**
6. SEC-06/07: lock at `onStop`, recents protection, FLAG_SECURE while locked, synchronous settings snapshot; fail-open only when `!isDeviceSecure`.
7. SEC-13/14/22: lock-aware NumberActionActivity (uniform UI or authentication first), a vault tile that authenticates before revealing, and FLAG_SECURE on widget configuration.
8. SEC-15/16: a shared `Bounded` reader with caps for setup files, QR gunzip, CSV, vCard cards and packs; an exact KDF count for QR and simple payloads.
9. SEC-12 (part): hook the permission guards to `preBuild`, switch the app to an allow-list, commit `verification-metadata.xml`, and add a minimal CI job.
10. SEC-18/19/21/26: `setHideOverlayWindows`; reject `file://` and own-authority stream URIs; notes links through UrlSafety; a confirm step for JOIN_CONTACT.

**Structural (1–3 weeks)**
